# Technical Debt Register

> Deferred compromises and known maintainability concerns. TD-01 to TD-04 were recorded by Member One in
> the M3 review (PED §1.16); TD-05 onward were added during M3 construction; TD-10 was added in M4.
>
> **M4 final status** (last column) is assessed against the M4 build (`m4-refinement`, evidence keys in PED §1.5.4):
> **Repaid**, **Partly repaid** or **Retained**. Retained debt is a deliberate choice for the final release, with its
> consequence stated; it is not hidden or marked complete.

| ID | Deferred compromise | Consequence | Mitigation / trigger to repay | M4 final status |
|---|---|---|---|---|
| TD-01 | Manager UI for Staff-account and Staff-group administration is deferred (ADR-05). Accounts and groups are seeded by `DatabaseStartup`. | Permission changes need a controlled alternative process (developer change + redeploy). | Document the process; build administration when group maintenance enters scope. | **Retained.** The controlled process was used in M4: `staff-general` and `staff-waste` with their groups were added by a reviewed code change and redeploy (`bdb89db`). Consequence unchanged: any account or permission change needs a developer. |
| TD-02 | Request types are plain strings in Staff-group permissions. | Naming inconsistencies could cause wrong access decisions. | Partly mitigated in M3: SQLite foreign keys force group categories to exist in `categories`, and the API stores the catalogue spelling (DEF-08). Move to controlled ids if categories become editable. | **Retained; risk mitigated while categories are fixed.** No API can edit categories or group permissions, foreign keys refuse unknown categories, and a client-supplied category is checked against the catalogue on the server. What remains is changeability: renaming a category would mean updating the text in several tables. Trigger (editable categories) not reached. |
| TD-03 | Manager policy grants visibility of all requests. | Department-specific reporting restrictions would need policy changes. | Revisit when a narrower Manager scope is agreed. | **Retained.** FR-012 is scored against this broad scope (§1.6.7). No narrower Manager scope was requested. |
| TD-04 | Small table-driven lifecycle may become insufficient if state-specific behaviour grows. | More operations could make guards and transition logic harder to maintain. | Follow ADR-04's trigger: reconsider when several operations depend on state. | **Retained; trigger approaching.** M4 added the first rule outside the transition table: only the current assignee may resolve (DEC-M4-01, a 6-line check in `TransitionService`), and reassignment depends on state. Still small and fully tested (`ResolutionOwnershipTests`, `ReassignmentTests`), but the next state-dependent rule should prompt the ADR-04 review. |
| TD-05 | SQLite instead of the M2 PostgreSQL target (ADR-07). | Single writer (DEF-09), no server-side availability features; performance results do not predict PostgreSQL. | `PostgresRequestRepository` behind the same `IRequestRepository`; re-run the integration, API and load tests against it. | **Retained.** Main reason NFR-003 is not met and NFR-004 is verified on SQLite only. The repository interface keeps the switch to one new class plus a re-run of the tests. |
| TD-06 | One shared demo password for all seeded accounts; no password change, lockout or MFA (ADR-08). | Acceptable for staging/demo only; not for production. | Per-user credentials with change/reset, account lockout, and MFA for Staff/Manager (RISK-001) before production. | **Partly repaid.** Each seeded account now has its own generated password; shared or short passwords are refused (`a721399`; `API11`, `API12`). Remaining before production: password change/reset, account lockout and MFA. |
| TD-07 | Simulated staging serves plain HTTP on localhost (`Security:RequireHttps=false`). | NFR-002 HTTPS is configured for Production but not exercised in any environment. | Run staging behind TLS (reverse proxy or Kestrel certificate) and add an HTTPS check to the deploy verification. | **Partly repaid.** `start.ps1 -Https` runs staging over HTTPS with the development certificate; redirect, Secure cookie and E2E verified (`889b0d7`, H1). Remaining: a certificate from a real certificate authority for production; HSTS cannot be observed on localhost; the HTTPS check is not yet part of `deploy.ps1`. |
| TD-08 | Schema is created with `CREATE TABLE IF NOT EXISTS`; no migration mechanism beyond `PRAGMA user_version`. | Future schema changes need manual scripts and careful backups. | Introduce versioned migration scripts before the first breaking schema change. | **Retained.** M4 made no schema change, so the trigger was not reached. |
| TD-09 | The browser UI is not covered by automated tests (E2E tests drive the HTTP API the UI uses). | UI-only regressions (e.g. a broken button) are caught only by manual demo. | Add a Playwright smoke test of login → submit → list once the UI stabilises. | **Retained; exposure grew.** The M4 UI changed substantially (`app.js` about +420 lines). Mitigated by API tests behind every UI action and a manual three-browser check (B1), but UI regressions still rely on manual checks. |
| TD-10 | Seeded demo passwords are stored in plain text in a local, git-ignored `seed-passwords.json` so demonstrators can read them (Development/Staging only). | Anyone with access to that machine's files can log in as any demo account. | Acceptable while only demo data exists and `Seed:Enabled=false` in Production. Repay with real account management (TD-01, TD-06) before any real users. | **Retained (new in M4).** Introduced with the TD-06 repayment; the database still stores only PBKDF2 hashes. |
